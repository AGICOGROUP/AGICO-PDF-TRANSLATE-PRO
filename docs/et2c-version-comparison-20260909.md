# ET 2C：本地版与 GitHub main 客观对比

审计日期：2026-09-09。范围：只读版本比较、原件/交付稿检查、现有基准复核和针对性测试；未回退代码、覆盖 Skill 或修改交付稿及其原 QA。

## 判断

这次交付稿不满足专业保版式翻译标准，应撤回此前“结构和签名均完整、全部验证通过”的结论。推荐停止把当前混合工作区当稳定发布版，以固定的 main 提交重建稳定基线，再择优保留有证据的性能及兼容性修复。没有依据把全部本地改进判定为失败，也不能保证直接 checkout main 就会改善这份文件。

未取得同一输入在云端旧版生成的对照 PDF，本次没有做两套系统的完整翻译 A/B。已经证实的是当前交付稿的缺陷及其代码/执行原因；“云端所有输出都更好”不是本审计的结论。

## 交付稿的实际问题

### 大白块擦除了结构

任务脚本 `tmp/pdfs/make_et2c_image_metadata.py` 将区域统一设为 `solid_fill`，并额外加入 BODY_CLEAN 大矩形。逐页合并清理矩形，计算其在原始 XObject 中的面积：

| 页 | 清理区占页面面积 | 实际变化像素占页面比例 |
|---|---:|---:|
| 1 | 33.95% | 31.36% |
| 2 | 53.07% | 48.29% |
| 3 | 65.23% | 53.17% |
| 4 | 65.76% | 27.18% |
| 5 | 69.42% | 31.51% |
| 6 | 69.16% | 24.88% |
| 7 | 69.45% | 27.26% |
| 8 | 69.71% | 28.92% |
| 9 | 66.51% | 34.69% |
| 10 | 53.28% | 46.50% |

这些比例不能单独证明结构损坏，因此进一步比对了第 5 页原始图与实际清理图。按 RGB 最大通道 <100 定义深色像素，原生坐标区间如下：

| 区域（原图像素坐标 x0,y0,x1,y1） | 清理前深色像素 | 清理后深色像素 |
|---|---:|---:|
| 左边框一段 (260,400,290,2500) | 30,766 | 0 |
| 左下手写签注区域 (285,2560,430,2780) | 2,273 | 0 |
| 页脚水平分隔线 (750,3020,2000,3040) | 12,240 | 198 |

原件与最终渲染同时证实左边框长段、左下手写笔迹和页脚表格线被擦除。这不是字号、对齐或纸张纹理的轻微变化，直接违反当前三项要求中的“关键结构完整”。

### 版面从技术文件变成稀疏居中段落

原稿的左对齐正文、缩进、条款/列表层级被居中段落替代，页脚单元格关系变弱。原因可定位到 `apply_image_vector_text.py`：横向文字始终调用 `drawCentredString`，没有正文对齐参数。该函数适合部分图内短标签，任务脚本却用它排整页正文；同时手工大框和预插入换行造成大片留白。

该函数的 `fitted_size`、`draw_horizontal`、`make_overlay` 与 main 的 AST 完全相同。因此，“新版新增了居中逻辑导致退步”不成立；本次错误使用既有能力是直接原因。

### 页脚仍有可读西班牙文字

原签署单位名称等普通说明文字被整体归入“签署审批栏”并保留。保留签字和徽记有合理性，但不能自动证明同一区域所有可读标签都属于不可翻译签章。此前只查 PDF 提取文本中的六个西语短语，无法检测图片里留下的西语文字；“未检出西班牙语正文”不等于整份文件无未译内容。

### 文件体积增加

原始前 10 页 PDF 为 17,866,523 字节，交付稿为 70,136,134 字节，约 3.93 倍。源 PDF 被克隆后又叠入全页清理图是相关机制之一。尺寸不变和文字可复制确实成立，但不足以支持保版式合格结论。

## 为什么 QA 通过却不合格

1. `reset_et2c_job.py` 将 194/194 个 manifest 文字块改为 `ocr-artifact`，native 重建阶段不再绘制它们；后续文字全走图像文字层。源 PDF 的这些文字确实全部采用不可见渲染模式 `Tr=3`，移除重复 OCR 层本身有依据；问题在于没有可靠地把其覆盖、格式和审查责任转交给新文字层。
2. 实际 `typography-report.json` 的 `checked_draws` 为 **0**，却有 `typography_matches_source: true` 和 `passed: true`。这是空检查通过，不能证明最终中文排版合格。
3. 本地 `verify_native_typography.py` 将 `passed` 改为恒真，格式差异移入 warnings。允许轻微格式差异是用户授权的目标，但“诊断执行成功”与“作品质量合格”的状态含义被混用。这次零对象问题在旧逻辑中也不能依靠格式严格度解决。
4. `make_et2c_final_reports.py` 直接将十页状态写为 passed，把结构、缺字、内容等失败列表写为空；该脚本不会检测对应问题。人工审查本可写报告，但其“结构完整”判断被原图对比证伪。
5. native runner 没有验证 `translation-review.json` 的逐项覆盖。这份记录使用全页泛化 ID，图像标签的源文则写作“对应区域西班牙语文本”，不构成逐项源文到译文的可追溯证据。
6. 清理脚本的报告实际上没有生成 `outside_region_pixel_changes` 字段，而 runner 使用 `.get(..., 0)` 汇总，缺失值被当作 0。本次独立像素比较确实测得区外变化为 0；但约 69% 页面被划为允许区，边框和签注在区内消失，这个结果仍不能证明结构完整。

这里同时存在本地改动和共同的旧漏洞：main 的 runner 同样信任人工布尔字段、不核验该语义记录，并用缺失字段默认 0。旧版严格门禁不是自动防止这种假阳性的保障。

## 路由和耗时根因

源文件十页均有一张扫描图；有文字的六页，其页面内容流文字显示操作全为不可见 `Tr=3`。原生字符量分布为 `[0,0,1375,15,1830,0,0,1808,1847,1454]`。

路由器只按提取文字是否非空来认定存在 native 内容，没有分辨“扫描图附隐藏 OCR”与“真正原生排版”。它因此把该文件交给 native/mixed 流程，重复承担正文与整页图片文字处理。路由器与 main 完全相同，直接回退仍会作相同选择。

本次实际执行没有使用 scan 适配器新增加的构建缓存等能力；却多次从 initialized 重跑 native、清图、组装和全量渲染。因此不能把此次超时直接归因于 scan 性能优化失败。任务执行反复变更策略及适配流程与输入不匹配是明确问题；本次没有可靠、完整的活动时间账本来分摊每个环节的总耗时。

## 哪些优化值得保留

已有 `tmp/scan-benchmark/build-measurements.json` 和 `before-process.json` 记录了同一 38 页样本的构建对比：旧构建 493.146 秒，优化后冷构建 66.141 秒、缓存构建 23.569 秒，清理图和文字/坐标差异页均为零。其基准提交 f5b1d57e 的 scan 构建、OCR 提取和分组脚本，与当前远端 main 对应文件字节一致。

这些是历史测量，本次没有重新跑 38 页完整翻译，不能把它们当作当前端到端速度保证。它们仍足以反对“所有新优化都应该丢弃”的判断。当前针对缓存/恢复、图像文字层及 native 布局相关测试实跑 **79 passed in 1.01s**，但这同样不能替代交付 PDF 的质量评估。

建议选择性保留：

- OCR 断点、清理底图缓存、局部背景采样和原子输出；
- 中文字体支持和空 native 页面修复；
- 有真实溢出证据才缩小该段落、保留其他段落基准字号；
- 轻微字号/字重差异和无实质遮挡的框相交作为提醒；
- 已通过审查页面复用、只重查修改区域。

建议撤销或替换：

- 本文档任务中的大白块、通篇居中、泛化源文标签和未经证据支持的通过报告；
- 以“所有块是噪声”规避文字覆盖/质量责任的做法；
- 验证对象为空或证据缺失却汇总为合格的逻辑。

扫描件附隐藏 OCR 的路由判定、正文应保持对齐及逐项覆盖转交，需要同时解决；这些属于新旧共同问题。

## 推荐决策

以固定 main 提交建立干净稳定基线，比继续在当前混合工作区叠补丁更容易复现和定位。完整保留现有工作作为可恢复记录，避免损失与本文件无关的 CAD 改进；只回移上述有证据的改动。

用同一前 10 页、同一模型/字体/运行环境做一次对照，按用户已经同意的三项标准直接看成品：内容正确、完整可读、结构完整。记录真实端到端用时。无需恢复所有苛刻字号门槛或增加一串审批；把现有判断落实到真实检查对象即可。

本次分析不支持继续把现交付稿作为合格成品，也不支持声称 main 未经验证即可必然达到旧云端观感。
