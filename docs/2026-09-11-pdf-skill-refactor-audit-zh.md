# PDF 翻译技能深度审计与重构建议

日期：2026-09-11。审计基线：`dade7e537b4ca36a8541b40de169b741bdcd68e2`。

本轮只分析、运行测试和无输出文件的诊断，不修改翻译引擎、Skill 规则或历史译件，不提交、不推送。下文区分已复现缺陷、代码层面风险和待实测的收益。

## 一、结论

值得继续建设，不建议推倒重写。当前项目的优势是：已经积累了真实文件上的处理能力、版面保护机制和一批针对性回归测试。短板是：这些能力尚未组合成足够稳定、省操作的执行流程，成品质量仍过度依赖执行者如何分组、填写中间数据、理解例外和检查上下文。

它更接近“有工具支撑的专业翻译工作流”，不是一个输入文件后即可稳定自主交付的翻译引擎。相同的工具与规则，并不能保证每次执行都做出相同的分组和排版判断。

重构方向应是：保留已验证的渲染与保护能力，重构翻译单元、任务身份、局部修复和复核衔接。不是把几个适配器硬合成一个，也不是继续增加检查文件。

用户提出的 30%–60% 提效有探索价值，但目前不能作出兑现承诺。建议统一按更严格的“端到端耗时减少 30%–60%”衡量，而不是仅计算脚本耗时或吞吐率增长。先在代表文件集上争取整体耗时减少 30%，再验证哪些类别能达到 50%–60%。简单且已经很快的文件，不宜承诺同样幅度。

## 三、值得保留的优势

### 1. 专用渲染路径基本合理

原生文档保留可选文字，扫描文件保护非文字像素，双语模式保留原文，原生 CAD 保留矢量结构。这些需求存在实际差异。强行使用统一的“全部栅格化、OCR、重画”方案，可能降低可选择性、工程线条质量和输出效率。

### 2. 质量原则已经趋于合理

`references/delivery-policy.md` 将阻断集中到内容正确、完整可读、关键结构完整。字号下限、轻微对齐变化、无害包围框相交等作为诊断，而不强求像素级排版一致；到限可以保留真实状态交付预览。这个方向应保留，不需要整体推翻门禁。

### 3. 有真实的缓存和恢复能力

扫描提取具备源文件绑定、逐页检查点和实现版本绑定；扫描构建缓存清理底图；CAD OCR 缓存切片；复核图片使用 display list 和内容绑定。不能把已经完成的优化再次作为未来收益承诺。

### 4. 最近的 CAD 短语合并是正确补缺

`merged / merged_into` 使多个原生文字片段能够按完整短语翻译、只绘制一次；组内试排失败时保留整组原文。它补上了“能读懂整句，但写回工具仍只能逐词摆放”的接口缺口。

### 5. 对失败的证据绑定已有基础

源文件、候选、复核记录间的哈希绑定，以及不允许伪造通过的规则，能防止不少旧成品、旧复核被误用的问题。应改善复用粒度，不应取消这些基本绑定。

## 四、缺陷与不足：按优先级排序

### P0：任务意图没有完整进入任务身份

**已确认的代码缺口。**

- `formats/pdf/native/scripts/v6_job_state.py:create_job` 以文件名和源文件哈希生成任务目录。
- `run_v6_job.py:init_job` 接收源语言、目标语言，但 manifest 已存在就直接复用，没有在此入口校验是否匹配本次目标语言。
- CAD `prepare` 也以源文件绑定恢复包；包结构没有把目标语言和输出模式作为完整恢复身份。

因此，同一源文件、同一 jobs_root 下从英文改中文，或者重复运行“全新测试”，存在误继承旧状态的风险。当前执行者可以用新目录规避，但不能只依赖记忆。

**最小改法：**任务身份至少绑定源文件、页范围、目标语言、输出模式；明确 `fresh` 与 `resume`。fresh 测试使用独立任务，不继承旧译文与复核。源图/OCR缓存与译文缓存分层；用户要求完全冷启动时连提取缓存也禁用。不要默认增加跨任务翻译记忆库。

### P0：已完整双语的快捷路径没有核对目标语言

**已复现接口缺陷。**

`formats/pdf/scripts/decide_drawing_translation.py:decide` 只核对中文、外语和成对数量。输入 10 条中文、10 条外语、10 对匹配、零漏项，即返回 `already_bilingual_complete`，不需要知道外语是英语还是西班牙语。根 Skill 也沿用了“中文加任一外语完整即保留”的表述。

风险案例：已有中英完整图，用户要求中西双语。当前快捷判断无法区分，可能错误跳过。这不是已经证明某份历史文件被跳过，而是代码没有表达这个必要条件。

**最小改法：**只有现有语言组合、用户目标组合及逐项覆盖都满足时才能直通。替换模式不能直通为双语成品。覆盖旧条款，不新增另一套冲突规则。

### P0：原生 CAD 的布局安全检查不对称

**已复现。**

`native_cad_pipeline.py:apply` 中，outline 分支会检查 `layout_box` 是否在页面内、是否邻近原文字；native 分支跳过了这段检查。

内存诊断：600×800 pt 页面，原文字位于 `[10,10,50,30]`，译文框设为 `[800,800,950,850]`。`validate_packet` 返回空错误列表，`insert_fitted_text(..., commit=False)` 返回字号 10。也就是“框内能装下”被当作试排成功，而没有确认框在可见页面中。本次未构建该错误最终文件，不声称它已通过完整终检。

**最小改法：**native 与 outline 共用最基本的有效框、页面边界、局部容器约束；合并短语必须受实际段落/单元格约束。优先在试排前纠正或拒绝错误几何，而不是靠最终截图发现消失的文字。

### P1：翻译单元仍过细，语义分组主要依赖执行者

CAD 提取以 PDF span 为记录单位。最新接口允许合并，但不会自动生成可靠的短语、编号条款分组；scan 的 `draft_blocks.py` 已有几何分组，却主要使用同行距离、列对齐、行距等启发式，不等于真实单元格或语义边界。

DESPIECE 历史 QA 显示通过，但用户截图展示了按源语言顺序摆中文词语、整句不连贯的问题。这既有执行者未做好语义复核的责任，也暴露出工具默认单元不适合目标语言重排的结构性问题。不能全部归罪于门禁，也不能靠多写一句“认真翻译”解决。

**建议：**原始 ID 作为证据保留，默认给执行者的是“整句/编号条款/单元格”的翻译单元；包含上下文、受保护数值、可用布局区域和原始成员。先建立保守分组建议，少量歧义再人工确认。不合并不同表格单元格，不因为相邻就合并尺寸和说明。

这同时改善质量和速度：减少碎片映射、重复填写、逐框调坐标和后续返工。

### P1：保护规则与上下文处理仍有张力

`is_protected('SE')` 当前返回 true。SE 既可能是仪表代号，也可能是西班牙语句子中的词。最新 Skill 已要求结合上下文，将误保护项改回 pending；但是执行路径要求修改 inventory 再把记录加入 packet。

规则文本已改善，因此不能说“完全没有修复”。剩余问题是：默认保护仍是硬状态，解除保护的操作较容易遗漏，重新 prepare 也需要关注重新提取与人工状态的协调。

**建议：**保留不可变提取事实，另存可解释的处理决定；将可能有语言歧义的短 token 作为候选保护，不在组句之前永久排除。无需引入通用语言识别大系统。

### P1：路由仍是页面尺寸和文字数量的粗启发式

`route_pdf_file.py:classify_document_kind` 主要使用大幅横向页面、宽高比、总字数及面积密度。

本次诊断结果：

| 输入特征 | 当前结果 |
| --- | --- |
| 842×595 pt，49 字 | document |
| 3430×1726 pt，49 字 | engineering-drawing |
| 上述大图再加一页 595×842 pt、4000 字文档 | 整份 document |

这不表示第一种页面一定是图纸，而是说明现有分类没有足够信息识别小幅图纸，也会受异构页面影响。`native-text` 只说明存在可见可提取文字，不证明主要待译文字都能提取；当前 Skill 已要求目视补充，但自动路由还没吸收这种判断。

**建议：**保留快速规则作为初判，只在疑似工程图、原生覆盖不足和异构页面上补充少量内容证据。输出每页能力信息和明确选路理由；不要仅继续调一个密度阈值。第一阶段仍保持一个任务一个主适配器，不急于开放多适配器拼装。

### P1：缓存粒度与失效规则不一致

- scan 提取缓存包含脚本哈希、OCR 包版本、DPI、源哈希等。
- CAD 切片 OCR 键为源哈希、页、DPI、区域及手写版本；全页 OCR 键为源哈希、页、比例及手写版本，未绑定 OCR 模型/依赖版本。
- CAD review bundle 把整个候选文件哈希和记录列表放进绑定；一个局部修改会使整个 bundle 失效。候选 OCR 也使用整文件哈希。

前者有升级后复用旧识别结果的风险；后者有局部修复重复全页/全文件工作的成本。当前扫描提取默认已经是单尺度，`--dual-scale` 是重试选项；不能再把“取消所有页面强制双尺度”算成待做优化。

**建议：**OCR缓存绑定提取能力版本/模型；排版绑定译文、字体和布局；复核绑定受影响页面内容。复用未变页面证据，组装完成后再绑定整份成品。先改实际热点，不建设大型通用缓存框架。

### P1：时间预算和局部修复仍主要靠 Skill 指令协调

共享政策已经要求扫描 120 秒/页、一次足够清晰 OCR、局部重试、到限交预览。但当前主要脚本没有一致的任务计时和剩余预算对象；例如扫描逐页渲染的 subprocess 没有显式 timeout。阶段耗时存在，不等于记录了翻译、工具间协调和复核的全部耗时。

**建议：**复用已有原生状态机经验，补一个薄的任务控制层：当前阶段、实际耗时、受影响页、可恢复错误、最新可读候选和下一步。预算用于提前调整修复范围，不用于把真实缺陷改成通过。修复时批量解决同类问题，避免一次只挪一个框。

### P1：复核的组织方式需要改善，而不是继续加门禁

CAD verifier 主要验证页结构、图片内容/位置、候选绑定及已填写的复核字段；它不理解译文语义。native/scan 有语义复核记录结构校验，也不能证明填报内容真实。CAD 参考文档已经明确承认这个边界。

**建议：**把零散裁剪的逐项检查，组织成完整页、整句/条款、表格行及异常区域的同一视图。首次保留全页覆盖；复修只看受影响单元和邻域，未变证据复用。数值、单位、否定条件等尽量提供差异提示。不要再增加“全部检查完毕”布尔字段或第二套同类报告。

已清楚可识别的正文漏译、中文方框字、实际跨列错位仍不能放行；原件本就模糊且合理放大后仍无法辨认的区域，定位说明后可以保留。这是基于原件能力的容错，不是降低可处理内容的标准。

### P2：环境和说明存在漂移

AGENTS 的适配器清单还只列三类；默认测试命令漏掉 native-cad 并遇到同名模块冲突；Python 3.12 的环境说明与本次实际 Python 3.14 不同。唯一发现的 requirements 文件没有列出 CAD 直接导入的 PyMuPDF，依赖未锁定。多个字体路径带有平台约定。

**建议：**覆盖过期说明，提供一个可复现的测试入口和经过验证的运行环境说明。使用轻量环境检查，提前告知缺字体/缺依赖；不要在正式翻译中临时更换翻译引擎、批量升级依赖。此项是 skill 可复现性问题，与机器人入口无关。

## 五、30%–60% 提速究竟应从哪里来

### 先排除误导性基线

历史 CAD 审计：复核渲染 14.782→1.425 秒；含 OCR 的完整复核 35.058→20.290 秒。这是一个旧任务的组件对比，没有重新翻译。

历史扫描审计：38 页 builder 493.146→66.141 秒，热缓存 23.569 秒；当时逐页双尺度 OCR 合计 864.863 秒。这不是当前版本的新文件端到端成绩。

DESPIECE 现有报告记录 prepare 81.123 秒、apply 6.182 秒。报告可能来自不同修复阶段，不能简单拼成一个端到端耗时，更不能拿文件修改时间差当作翻译耗时。它至少提示：继续把几秒钟的 apply 优化一半，未必能解决用户等待很久的问题。

### 优先优化顺序

1. **一次生成合适的翻译单元和布局建议。**减少碎片级决策与返工，兼顾质量与速度。
2. **局部修改、局部重算、局部复核。**保留全覆盖但不重复已确认的未变内容。
3. **将可靠的串联步骤合成少量稳定命令。**减少猜路径、手填重复字段、重复加载上下文和因接口误用而重试。
4. **依据实际漏识别区域补充 OCR。**保留必要覆盖，避免默认多次全页识别；CAD 的切片加全页补充不能未经对照直接删除。
5. **最后再考虑页级有限并发。**先测 CPU、内存和 OCR 线程行为。扫描大图并发可能因内存压力更慢，不能直接承诺多开进程即提速。

收益不可逐项相加：同一轮返工同时涉及识别、排版和复核，属于重叠时间。举例，若可优化部分占总耗时 60%，该部分减半，端到端只能减少 30%；要减少 60%，必须覆盖更大比例或大幅减少原本的无效返工。这是算术说明，不是本项目已测占比。

## 六、三个方案的取舍

| 方案 | 优点 | 主要风险 | 判断 |
| --- | --- | --- | --- |
| 继续打补丁、加说明 | 短期成本低 | 继续依赖执行者记住例外，收益不稳定 | 仅用于上述直接缺陷，不作为整体路线 |
| 保留适配器，重构任务与语义/布局衔接 | 可复用已有能力，能分阶段对照与回退 | 需认真设计几个核心数据字段 | **推荐** |
| 全部重写成统一引擎/统一栅格流程 | 表面接口一致 | 丢失成熟能力，长时间回归，难证明质量不降 | 当前不推荐 |

推荐方案的最小主线是：任务意图与版本固定 → 提取事实与翻译单元 → 整句翻译及约束排版 → 局部修复与一致交付状态。沿用现有执行器，不先搬动全仓文件、不引入复杂服务、数据库或多模型调度。

## 七、实施与验收顺序

### 第一步：建立可信对照，修正直接缺陷

固定 main 的运行目录与依赖，实验版留在 codex；当前 Junction 不足以隔离。统一测试命令；新增目标语言切换、双语语言匹配、native 页外框的负例测试，然后最小修复。补一份简单阶段计时，先知道时间花在哪里。

### 第二步：优先改造 CAD 翻译单元与局部布局

沿用刚加入的 merged 能力，提供条款/单元格分组建议与容器约束。用 DESPIECE 的整句错序、俄文企业表格的跨列/Logo覆盖等作为挑战样本。旧 DESPIECE 成品不能当质量金标准，因为用户已明确指出缺陷。

### 第三步：扫描局部修复和证据复用

以 10 页 ET 2C 和 Pictures 类文件验证：改一处不触发全量识别和重复审查；重叠误报只针对精确局部解除；原件模糊项定位保留；清晰技术条款不能因 OCR 漏读而被跳过。

### 第四步：在数据证明必要时优化 OCR 和并发

确认实际瓶颈后再调整切片、比例、模型生命周期及有限并发。不同类别单独对照，不以扫描提速掩盖 CAD 变慢。

- 扫描工程图/低清局部：Pictures；

### 如何证明“不降低质量而提速”

两版使用相同输入哈希、页范围、目标语言、模式、模型设置和运行环境。新翻译对照不复用旧译文；冷启动与同任务恢复分别记分，不混在一起。先小集摸底，稳定后每个代表样本至少做配对重复，降低模型和工具等待波动的影响。

记录总主动耗时、首个可读候选时间、修复轮数、正式交付/预览/失败数量及各阶段耗时。失败任务消耗的时间必须计入，不能只展示成功且最快的样本。

人工对照关注完整技术含义、清晰内容覆盖、数字/单位/否定条件、表格关系、图线和图内文字、字体可读可选及附近布局。数值与结构差异检测作为辅助，不用 OCR 零残留或 JSON 通过代替审阅。

全套耗时缩减以同样任务集合的总耗时计算，并同时报告每类中位数和最慢样本；正式交付率不能下降，新增严重错误必须修复。30% 是第一阶段候选目标，60% 是后续条件性目标，不作为所有文件的硬承诺。

## 八、哪些事情现在不做

- 不降低 DPI、缩小所有字体来换取速度。
- 不删除首轮全页覆盖与清晰技术内容复核。
- 不把预览算成正式成功，不把可恢复错误当成不需要修复。
- 不引入跨任务旧译文复用来“赢得”全新翻译测试。
- 不为一个文件增加全局特例，不继续到处调整统一密度/字号阈值。
- 不在翻译任务中修改底层 skill，避免同一任务跨版本执行。
- 不改机器人流程；这里只统一 skill 自身的结果状态和候选定位。
